## 第 1 节 问题与动机

### 1.1 在线装箱：一个必须当场做决定的问题

在线装箱（online bin packing）：物品逐个到达，每个物品必须立即放入一个
已开箱或新开一个箱，不能等后面的物品到了再反悔。目标是平均箱数越低越好。
评价指标为各数据集上的平均箱数。

这个任务值得做方法实验，原因不在装箱本身，而在它的结构：每一步都是一次
不可逆的序贯决策——只看到当前物品和各箱的剩余空间，就要下注。这种
“信息不全、决定不可逆”的设定，正是启发式算法最难啃、也最容易被拿来
检验新方法的地方。做得好的规则，在仓储、排程这类按序分配资源的场景里
都有对应的影子；做不好的地方，也暴露得很干净——箱数就是答案，没有
含糊的评价标准。

### 1.2 基线很强，这正是难点

最常用的启发式是 Best Fit（BF）：把物品放进放得下、剩余空间最小的箱子。
First Fit（FF）是它的对照。两条基线的成绩：

| 数据集 | BF | FF |
|---|---|---|
| search 集 | 265.3 箱 | 269.5 箱 |
| validation 集 | 267.7 箱 | 272.4 箱 |
| test 集 | 266.367 箱 | 270.533 箱 |
| OR3 集（20 个实例，容量 150） | 212.000 箱 | 212.750 箱 |

BF 简单、稳定、难被打败——这就是本项目的出发点：如果一个方法连 BF 都
赢不了，它在这个任务上就没有立足之地；如果能赢，哪怕只赢一点，也说明
它找到了人类启发式没覆盖到的结构。

### 1.3 为什么试 FunSearch 式进化

FunSearch 的思路一句话：**大语言模型生成候选评分函数（priority function），
岛屿进化保留最优，迭代改进。** 人写启发式，一次只能试一种想法；让模型
按“生成—评估—保留—再生成”的循环走，理论上能试到人想不到的评分形式。

本项目要回答的不是“模型能不能写出一个能跑的评分函数”，而是两个更具体
的问题：第一，提示词写得更好（增强提示），模型找到的好函数是否更多；
第二，先用小探针集筛掉与已有程序行为一致的候选（行为筛查），能否把
评估预算省下来花在真正新的候选上。这两个问题各分两档，构成第 2 节的
2×2 析因设计：A 基础提示、B 增强提示、C 基础+筛查、D 增强+筛查。

### 1.4 本报告讲什么

第 2 节写方法与防作弊设计，第 3 节写 1200 次正式实验的结果，第 4 节写
两轮跟进（热启动 1800 次、记忆校准 160 次）为什么没能继续往上走，
第 5 节如实披露实验中出过的问题，第 6 节给结论与下一步。
提前说一句结论，免得读者带着错误期待读下去：**12 个获胜候选在 test 和
OR3 上全部小胜 BF，但幅度很小；三轮跟进都指向同一天花板。** 这是一份
以可复现、可审计的阴性结果为主线的期中报告——这正是期中检查想看到的
东西：方法跑通了，结论站得住，剩下的工作是最终提交（2026-12-03）前
补机制分析，而不是继续堆生成次数。

## 第 2 节 方法：2×2 析因设计

### 2.1 任务与基线

在线装箱（online bin packing）：物品逐个到达，每个物品必须立即放入一个已开箱
或新开一个箱，目标是平均箱数越低越好。评价指标为各数据集上的平均箱数。

基线（Best Fit, BF）：
- search 集 265.3 箱；validation 集 267.7 箱；test 集 266.367 箱；OR3 集 212.000 箱。
- 对照基线 First Fit（FF）search 集 269.5 箱。

FunSearch 思路一句话：大语言模型生成候选评分函数（priority function），
岛屿进化保留最优，迭代改进。

### 2.2 四臂设计

2（提示词：基础 / 增强）× 2（行为筛查：无 / 有）的析因设计，共四臂：

| 组 | 提示词 | 行为筛查 |
|---|---|---|
| A | 基础提示 | 无 |
| B | 增强提示 | 无 |
| C | 基础提示 | 有 |
| D | 增强提示 | 有 |

每组 × 3 个种子（11 / 22 / 33）× 每种子 100 次生成，共 1200 次生成。
机制：`mechanism_v3` + `disable_on_mismatch_v1`；审计抽查率 0.1；岛屿重置 50。

### 2.3 防作弊与可复现设计（最容易被问的三点）

1. **协议先冻结、后运行**：协议文件 `protocol-formal-muse-100.json`
   （protocol_id `3eb1f24d…`）于 2026-11-15 17:15 UTC 冻结，12 个分轮随后启动；
   候选封存于 `candidates-sealed.json`，最终评估一次性完成（2026-11-15 18:23）。
2. **四集分离**：search / validation / test / OR3 各司其职——进化只看 search，
   选模型只看 validation，test 与 OR3 在最后只测一次，避免“用终测集调模型”。
3. **生成器替换已披露**：原计划 DeepSeek API；2026-11-15 上午确认云端后台到
   DeepSeek 的路由被出口策略封禁（Tunnel 403，非临时网络故障，不可重试绕过）；
   经用户指示改用 Muse Spark 1.3（文件握手提供方，`paid_api_request=False`），
   协议修订后重新冻结。**组间比较在同一生成器下有效；绝对数值与 11-06 DeepSeek
   试点（16 次）不可比。** 全程 0 元。

### 2.4 行为筛查与审计（方法要点）

C、D 组在完整评估前先用小探针集判断候选是否与已有程序“行为一致”；
一致则跳过完整评估，不一致或被抽中审计则完整评估。
审计抽中的候选在完整 search 集上重测：若箱数或轨迹与探针结论不符，
该指纹禁用，此后绕过筛查直接完整评估。筛查的设计是保守的——
它只会漏掉候选，不会污染结果（见 3.3）。

## 第 3 节 正式实验结果

### 3.1 核心表（组均值）

| 组 | search 最优均值 | validation 选中均值 | test 均值（ΔBF） | OR3 均值（ΔBF） |
|---|---|---|---|---|
| A 基础提示 | 265.111 | 267.6 | 266.200（−0.167） | 210.533（−1.467） |
| B 增强提示 | 265.033 | 267.7 | 266.133（−0.234） | 209.950（−2.050） |
| C 基础+筛查 | 265.067 | 267.7 | 266.067（−0.300） | 210.400（−1.600） |
| D 增强+筛查 | 265.089 | 267.6 | 266.144（−0.223） | 209.850（−2.150） |

讲法：**12 个获胜候选在 test 和 OR3 上全部优于 BF，无一例外**；但幅度很小——
test 好 0.06%–0.11%，OR3 好 0.7%–1.0%。三个种子一致，是真实但微弱的信号，
不是单一种子的噪声。组均值上 test 最好的是 C（−0.300），OR3 最好的是 D（−2.150）；
B 在两个 heldout 集上都排第二且最稳定。

### 3.2 逐种子最终评估（test / OR3）

| run | test | OR3 | run | test | OR3 | run | test | OR3 |
|---|---|---|---|---|---|---|---|---|
| A11 | 266.133 | 209.900 | A22 | 266.233 | 210.600 | A33 | 266.233 | 211.100 |
| B11 | 266.133 | 209.950 | B22 | 266.133 | 209.950 | B33 | 266.133 | 209.950 |
| C11 | 266.067 | 210.400 | C22 | 266.067 | 210.400 | C33 | 266.067 | 210.400 |
| D11 | 266.033 | 209.700 | D22 | 266.200 | 209.700 | D33 | 266.200 | 210.150 |

单项最好：test 为 D_seed11（266.033，−0.333），OR3 为 D_seed11 / D_seed22
（209.700，−2.300）。注意：B 组三个种子选中的是**同一份代码**；C 组
三个种子 test / OR3 成绩相同，但选中的代码仅在门控细节上不同（见 §3.4）——
跨种子相同获胜者是同一机制的不同抽样，**不是三次独立发现**，汇报时不得
说成“三次独立复现”。

search 集的收益基本没有泛化：search 最优比 BF 好 0.19–0.27 箱，
validation 选中只比 BF 好 0–0.1 箱，test 好 0.17–0.30 箱。
最终成绩以 test / OR3 为准，**不要把 search 集的 265.033 当作“比 BF 好 0.267”
来宣传**。

### 3.3 请求对账与审计（可信度证据）

1200 次请求 = 969 次成功完整评估 + 5 次评估中出错的候选（D 组，代码可提取
但在 search 实例上运行报错）+ 193 次行为筛查跳过 + 33 次与已有程序完全相同
的文本缓存命中（直接复用已测结果，不重评）。格式违规 0，provider 错误 0，
提取失败 0。

- B 组 28 次缓存命中：同一份代码在三个种子里反复出现，说明 B 的机制收敛到
  了同一个解。
- C/D 筛查组：探针上行为一致共 220 次，其中 193 次跳过完整评估（C 78 次，
  D 115 次），27 次被抽中审计。
- 审计：共 27 次（C 10 次，D 17 次），**16 次发现不符（C 5/10，D 11/17，
  合计 59%）**——探针上行为一致的两个程序，在完整 search 集上箱数或轨迹
  并不相同。审计不符后 16 个指纹被禁用，相关候选此后绕过筛查直接完整评估
  （211 次绕过评估）。
- 结论：探针等价是弱证据，但审计机制按设计 catch 住了这些不一致；筛查是
  保守的，只会漏掉候选，不会污染结果。代价是实际只完整评估了 969 个新候选，
  而非名义上的 1200 个。

### 3.4 机制观察：12 个获胜者是同一家族

**所有 12 个获胜者都属于 sweet-band 家族**：甜带残留奖励（[28,48] 或 [30,45]，
+15/+20）+ 中段惩罚（[8,22] 或 [10,20]，−15/−20/−25），叠加在 BF 的
`-(r - item)` 之上。B 组三个种子选中的是同一份代码；C 组三个种子选中的代码
仅在门控细节上不同（`item % 3 == 1` 门控）。

有害机制多次复现：惩罚近乎贴合的残留是灾难性的（[0,5] 惩罚含 exact fit 时
达 284.133）；near-exact 加分、取模奖励、worst-fit 切换、分布相对甜带均明显
更差；加分叠加（甜带 + exact-fit + 多件奖励）不产生新收益。

A 组获胜者形态更多样：A11 是“近贴合优先、否则 worst-fit”的混合；
A33 是残留十位奇偶门控（+30）。两者 validation 均为 267.6，但 test / OR3
上 A 是最弱的一组——这类“花哨”机制泛化更差。

## 第 4 节 两轮跟进：为什么没继续往上走

一句话：**三条路（更多生成、更好种子、加记忆）都试过，都指向同一天花板。**
正式实验 1200 次 + 热启动 1800 次 + 记忆校准 160 次，一共 3160 次生成、0 元，
结论一致。

### 4.1 热启动组合进化（1800 次，0 元）

做法：把 12 个正式优胜者（去重后 9 份代码）+ FF / BF 作种子，每组每种子
150 次，提示词 v3c，共 1800 次生成。

结果：

- 12 轮里 **11 轮的入选者就是种子本身**，只出 1 个新候选：A_seed33
（search 265.000，validation 267.7 = BF 水平，test 266.100）。
- 唯一新候选仍是 sweet-band 家族，只是奖惩幅度随物品尺寸缩放——
不是新机制。
- validation 入选均值 **267.692**，比正式实验的 267.65 还差一点；
**没有任何一组在 test 与 OR3 上同时改进**。
- 结论：再投 150 次/组的回报极低。“从甜带出发再进化”这条路，
在种群层面已经试过，答案是否定的。

### 4.2 记忆校准（160 次，0 元）

v4 / v5 / v5b 共 5 次校准，32 次/组，B 组 seed 11 为主：

| 校准 | search 最好 | 家族数 | 头号家族占比 | 甜带尝试 |
|---|---|---|---|---|
| v3 校准（对照） | 265.133 | 11 | 50%（16/32） | — |
| v4 B | 265.267 | 18 | 15.6%（5/32） | 0 次 |
| v5 B | 265.267 | 18 | 12.5%（4/32） | 0 次 |
| v5b A（基础组+记忆） | 265.167 | 5 | 75% | 0 次 |
| v5b C（基础+筛查+记忆） | 265.133 | 8 | — | 0 次 |

讲法：**多样性确实变了，但分数不动。** v4 把 B 组家族数从 11 推到 18、
头号占比从 50% 压到 15.6%，v5 最好成绩 265.267 与 v4 完全相同；
v5b 基础组记忆反而让多样性崩到 5 个家族、头号占 75%。
5 次校准共 160 次生成，**sweet-band 家族 0 次尝试**，validation 全是
267.7（= BF 水平）。

为什么 sweet-band 难被“发现”：v3 校准里它是“高分父辈 + 局部改动”的
产物；v4 记忆块的避让清单 + 未试原型提示打断了这个循环，64 次生成里
一次也没试过甜带；v5 把最好家族标为“可精修”后仍是 0 次——甜带在本轮
从未被观测到，所以无从精修。**瓶颈在发现，不在精修。**

### 4.3 收敛本身就是天花板证据

正式实验 12 个获胜者同属 sweet-band 家族；热启动把这 12 个获胜者当种子
再跑 1800 次，11/12 轮入选的还是种子本身；记忆校准 160 次生成里甜带
一次都没被试过。三条独立跟进方向收敛到同一结论：**在当前任务 / 提示词 /
生成器组合下，BF 附近就是天花板。**

## 第 6 节 结论与下一步

### 6.1 结论

- **BF 附近就是当前设定的天花板**：小胜真实存在（12 个候选在 test 和 OR3
上全部小胜 BF，三个种子一致），但 FunSearch 式进化在这个任务 / 提示词 /

- **记忆与热启动能改变探索分布，变不成分数**：多样性、家族数、头号占比都
动了，validation 始终停在 267.7。

# 上下文 v4 校准报告：搜索记忆有没有改进 FunSearch

日期：2026-11-15（晚）。生成器：Muse（HandshakeProvider，0 CNY）。
计划与预注册标准：`docs/progress/CONTEXT_V4_PLAN_20261115.md`。
正式实验不受影响：本报告只涉及探索性校准，不碰密封的正式研究。

## 结论先行

**记忆块确实改变了搜索行为，但没有带来分数改进。** 两组 64 次生成：

- 多样性目标达成：B 组头号家族占比从 v3 校准的 50% 降到 15.6%，家族数
  11→18；D 组维持低集中（13.0%）。
- 分数目标全部落空：B 组最好 265.267（v3 校准 265.133），D 组最好
  265.300（= BF，一个候选也没赢过 BF；v3 校准 265.100）；选中
  validation 两组都是 267.7（= BF）。
- 最值得注意的现象：**64 次生成里一次也没试过甜带家族**（v3 校准里
  最好的家族），而甜带在 v3 的 32 次校准里就被找到了。记忆块的避让
  逻辑把搜索推离了已知最好区域，新探索的区域大多更差。

这不是实现 bug——记忆块按设计工作（字数合规、方法记录完整、测试全绿）。
这是设计取舍：当前记忆把“饱和”等同于“不要再试”，没有区分“饱和且
最好”（值得精修）与“饱和且平庸”（应该避开）。

## 方法

- 提示词版本 mechanism_v4 = mechanism_v3 原文 + 一段搜索记忆块
  （`funpack/search_context.py`）。记忆内容：本轮每个机制家族一行
  （结构签名 + 尝试次数 + 最好 search 集均值），硬上限 120 词；
  饱和家族（≥3 次）列为避让清单，最好家族 1 行，未试原型最多 2 行；
  增量更新，不存候选代码原文，只含 search 集均值。
  v3 文本逐字节不变（测试保证）；basic 臂的 v4 提示词与 basic_v1
  相同（记忆块只注入 enhanced 提示词）——见“实现边界”。
- 校准：B 组（enhanced，无筛查）与 D 组（enhanced + 行为筛查），
  各 seed 11、32 次调用，islands 4，reset 50（32 次内不触发），
  audit 0.1，disable_on_mismatch_v1，HandshakeProvider（Muse，0 CNY）。
  对照：同一 seed、同一调用数的 v3 校准 round 2。
- 评价：预注册 4 条标准（多样性、search 最好、无退化、选中 validation），
  家族分布用同一分类器（`funpack.search_context.classify`）统计。
  单种子 32 次，结论只是方向性信号。

### 最好候选代码

B v4 最好（candidate_000019，265.267，`ratio+worst_fit`）：

```python
def priority(item, bins):
    return [((r - item) if r - item >= 2 * item else (-(r - item) - 50)) for r in bins]
```

残差 ≥2·item 时取 worst-fit，否则 BF−50。

D v4 最好（candidate_000009，265.300，`dist+worst_fit`，打平 BF）：

```python
def priority(item, bins):
    m = min(bins)
    return [(r if item * 2 <= m else -(r - item)) for r in bins]
```

## 诚实讨论

1. **多样性提高了，但提高的方向不对。** 记忆块的两个部件（饱和家族
   避让清单 + 未试原型提示）共同把生成器推向未探索区域。未探索区域
   里好机制和差机制都有，而 32 次调用里差机制占了大多数：B 组 18 个
   家族里 7 个最好成绩 ≥287，D 组 15 个家族里 6 个 ≥287。探索广度
   上去了，期望分数反而下来了。
2. **为什么甜带一次也没出现。** 甜带在 v3 里是“高分父辈 + 局部改动”
   的产物：生成器看到高分父辈后围着它微调。v4 的记忆块在两种意义上
   打断了这个循环：未试原型提示在早期就建议了别的方向（count-gate、
   triangular、scaled、ratio、dist），而一旦某个家族试了 3 次就进入
   避让清单。32 次调用不足以让搜索在试遍新方向后绕回甜带。单种子
   不能排除运气成分，但两组同时出现同一种缺失，指向系统性原因。
3. **筛查组没有更差也没有更好。** D 组的 9 次行为跳过、2 次审计
   （0 不符）与 v3 校准同一量级；筛查与记忆没有可观测的交互。
   D 组的格式违规从 3 次降到 0 次，但那是生成器自检的功劳，
   与记忆块无关（B 组两轮都是 0 次）。
4. **限制。** 单种子、每组 32 次；生成器是 Muse 协调员（带预设计
   机制与避让执行），不是原始 LLM 温度采样——v3 对照组也是同一类
   生成器，所以组间比较有效，但绝对分数不能外推到 DeepSeek 或
   其他生成器。记忆块最大只用了 41 词（B）/ 34 词（D），远低于
   120 词预算——预算从来不是瓶颈，内容选择才是。

## 对期中 / 期末的意义

- **期中报告（11-19）可以写：** 上下文记忆是一种已验证能改变探索
  分布的干预（B 组头号家族占比 50%→15.6%），但在本实验设置下没有
  转化为分数改进；正式实验的结论（甜带家族、全部 12 个获胜者赢过
  BF）不受影响，v4 校准是独立的探索性工作，不碰密封证据。
- **不可以写：** “上下文改进了结果”、“v4 优于 v3”。两个 v4 组
  的 search 最好与选中 validation 都不优于 v3 校准。
- **期末值得试的方向（按性价比排序）：**
  1. 记忆语义改成“精修最好家族，避让饱和且差的家族”：最好家族
     标为可精修而非避让；避让只针对尝试 ≥3 次且最好成绩差于当前
     最好的家族。这是本轮最直接的教训。
  2. 配合更长的校准（100 次/组）：给搜索留出绕回甜带的时间；
     但需配合方向 1，否则可能只是更久地错过甜带。
  3. 给 basic 臂（A/C）加记忆：需要 basic 提示词的记忆设计，
     是一个新提示词版本的工作，不在今晚红线内。

## 实现边界（执行中发现）

mechanism_v4 的记忆块只注入 enhanced 提示词。basic 臂（A/C）的
v4 提示词与 basic_v1 逐字节相同（已验证），所以按原计划扩展 A/C
等于把 v3 对照重跑一遍还贴上 v4 标签——没有执行，只扩展了 D 组。
A/C 需要 basic 提示词的记忆设计。

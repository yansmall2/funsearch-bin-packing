# 上下文 v4 校准计划（跑前写定，跑后填结果）

## 动机

正式实验的回答里指出的第 3 个原因：搜索很快收敛到同一个机制家族。
用新写的家族分类器（`funpack/search_context.py::classify`）在旧数据上量了一下，
确认了这一点——不是感觉，是数字：

- 校准 round 2，B 组 seed 11，32 次调用：11 个家族，但头号家族
  `exact_fit+ratio+scaled` 占了 16/32（50%），加上同族的 `exact_fit+scaled` 4 次，
  同一结构家族合计 20/32。
- 正式 B 组 seed 11，100 次调用：90 次有效评估，40 个家族，但头两个家族
  （甜带 `[8,22];[30,45]` 与 `[8,22];[28,48]` 的 count_gate+exact_fit+ratio 变体）
  合计 32/90（36%），另有 10 次完全重复（text cache hit）。
- A 组最分散（26–29 个家族/100 次），C/D 居中。

生成器每次只看到 2 个父辈，不知道已经试过什么，所以围着高分家族打转。
办法不是把历史全堆进提示词，而是给一份**压缩过的搜索记忆**。

## 上下文实现方法（防堆积的设计）

`funpack/search_context.py`，新提示词版本 `mechanism_v4` = v3 原文 +
插入一段搜索记忆。v3 文本逐字节不变（测试保证）。

- **存什么**：每个机制家族一行：结构签名 + 尝试次数 + 最好 search 集均值。
  不存任何候选代码原文，不存完整历史。
- **家族定义**：结构，不是常数。AST 提取残差窗口（`r-item` 上的常数区间）
  + 结构标志（mod/count_gate/triangular/scaled/ratio/exact_fit/dist/worst_fit）。
  同窗口同标志 = 同家族，改常数、换写法（`and` 与链式比较）不算新家族。
  已验证：B 组获胜代码的常数变体与链式写法分到同一家族。
- **选什么**：渲染时按优先级取：饱和家族（尝试 ≥3 次）列为避让清单（最多 3 行）、
  最好家族 1 行、本轮未试过的原型（固定词表）最多 2 行。
- **预算**：硬上限 120 词。超了先删未试提示，再删多余的饱和行；
  标题与最好家族行永不删。增量更新，每次观测 O(1)，不重扫历史。
- **范围**：只属于本次运行，只含 search 集均值；validation/heldout/test
  结果永不进入，与父辈反馈的红线一致。
- **证据**：每条请求的 `search_context_words` 记在 events.jsonl；
  最终家族表写 `search_context.json` 与 final_info.json；method 记
  `search_context: mechanism_v4_memory_v1`。

## 对 frozen 协议的影响（已说明）

`prompts.py`、`search.py`、`protocol.py` 是正式协议 `protocol-formal-muse-100.json`
（protocol_id 3eb1f24d…）的 frozen 文件。改动是加法（v3 路径不变），
但新代码的源码哈希与冻结值不同，**旧协议不能再用新代码重新 load**。
正式实验的密封证据不受影响：分支 `fatbaby/smoke-test-20261114` 在
`dd8f254a` 完整保存了当时的代码与密封产物，可检出复核。
本次校准不走协议，是独立的探索性运行。

另：初版接线曾漏改 `protocol.py` 的 `expected_method`（seal 时方法字典
精确比对），导致 5 个协议测试报 “run method versions differ from protocol”。
已修复：`expected_method` 按 plan 的版本推导 `search_context` 键
（v4 → mechanism_v4_memory_v1，否则 off），171 个测试通过后才继续。
教训：方法字典是密封比对的一部分，改 search.py 的 method 必须同步改
protocol.py 的期望值。

## 校准设计

- 组：B（enhanced），seed 11，32 次调用；islands 4，reset 50（32 次内不触发，
  与校准一致），audit 0.1（B 组无筛查，不适用），mechanism_v4，
  disable_on_mismatch_v1；HandshakeProvider，0 CNY。
- 输出目录：`run_muse_ctxv4_B_seed11/`；握手目录：`handshake-ctxv4/`。
- 对照（同一分类器、同一 seed、同一调用数）：
  校准 v3 B seed 11：best 265.133，32 次评估，11 个家族，头号家族 16/32，
  0 重复，0 格式违规，选中 validation 267.7。
  正式 v3 B seed 11（100 次）：best 265.033，90 次评估，40 个家族，
  头两家族 32/90，10 次重复。

## 跑前写定的成功标准（单种子，32 次，噪声大，只看方向性信号）

1. 多样性：头号家族占比 < 50%（v3 校准为 16/32），且不同家族数 ≥ 11。
2. 质量：search 最好 ≤ 265.100（优于 v3 校准的 265.133）。
3. 无退化：provider 错误 0，格式违规 0，完全重复 ≤ 2。
4. 次要：选中 validation ≤ 267.6（优于 v3 校准的 267.7）——单种子，仅作参考。

若 1 不成立，说明记忆块没能改变生成器的探索分布；若 1 成立但 2 不成立，
说明多样性提高了但没转化为更好的分数。两种情况都如实写进报告。

## 结果（B 组先行，2026-11-15 晚）

### B 组 seed 11，32 次，mechanism_v4（已完成）

- 运行：`run_muse_ctxv4_B_seed11/`，termination `request_budget_completed`，
  32/32 请求，0 provider 错误，0 格式违规，0 完全重复，32 次有效评估。
  方法 `mechanism_v4 / search_context mechanism_v4_memory_v1`，
  `search_context_max_words` 最大 41 词（预算 120，从未触顶）。
- 家族分布（`classify`，32 个候选）：**18 个家族**，头号家族 `ratio` 5/32
  （15.6%），其次 `plain` 4、`triangular`/`mod`/`dist+triangular` 各 3。
- search 最好：**265.267**（candidate_000019，`ratio+worst_fit`：残差 ≥2·item
  时取 worst-fit，否则 BF−50）。选中 validation：**267.7**（与 BF 持平）。

### 初步解读

多样性目标大幅达成（头号家族占比 50%→15.6%，家族数 11→18），
但分数没有跟上，反而略差（265.267 vs 265.133）。一个关键观察：
v4 本轮**一次也没试过甜带家族**——家族表里没有
`windows[8,22];[28,48]` 或 `[8,22];[30,45]`。记忆块的避让清单把搜索
推离了已知最好的区域，而新探索的区域大多更差（多个家族最好成绩
在 277–295 之间）。多样性提高了，但提高的方向不是朝向更好的分数。
单种子 32 次，结论只是方向性信号。

生成器中途一次中断：请求 28 时避让规则过严导致脚本中止（剩余设计
全带 banned token）；已修复为分层选择（先严格避让，无可用时取重叠
最少者，永不中止），28～32 补答完成。教训已记入 D 组简报。

### 扩展决定

标准 1 成立，按计划扩展。但核查发现一个实现边界：**mechanism_v4
的记忆块只注入 enhanced 提示词；basic 臂（A/C）的 v4 提示词与 basic_v1
逐字节相同**（已验证：`build_messages('basic', …, 'mechanism_v4',
search_context=…)` == `build_messages('basic', …)`）。用 v4 跑 A/C
等于把 v3 对照重跑一遍还贴上 v4 标签，比较是空的。因此 A/C 不跑，
只扩展到 D 组（enhanced + 筛查，记忆块真实生效）。A/C 需要 basic
提示词的记忆设计，那是新提示词版本，今晚红线内不做。

## D 组结果（2026-11-15 晚，已完成）

- 运行：`run_muse_ctxv4_D_seed11/`，termination `request_budget_completed`，
  32/32 请求，0 provider 错误，0 格式违规，0 完全重复；23 次有效评估，
  9 次行为跳过，2 次审计（0 不符），方法 `mechanism_v4 /
  search_context mechanism_v4_memory_v1`，`search_context_max_words` 最大 34 词。
- 家族分布（`classify`，23 个已评估候选）：**15 个家族**，头号家族
  `triangular` 3/23（13.0%），其余 `count_gate+dist+triangular`、`ratio+scaled`、
  `dist+worst_fit`、`mod` 各 2。
- search 最好：**265.300**（= BF，一个候选也没赢过 BF；最好候选
  candidate_000009 265.300，`min(bins)` 门控的 worst-fit 回退）。
  选中为 seed_bf 本身，validation **267.7**（= BF）。

### 两组合并结论

- 记忆块确实改变了探索分布：B 组头号家族占比 50%→15.6%、家族数 11→18；
  D 组维持低集中（13.0%）。但**两组 64 次生成里一次也没试过甜带家族**
  （家族表里无 `windows[8,22]`），而甜带是 v3 校准里最好的家族。
  避让清单 + 未试原型提示把搜索推离了已知最好区域，新探索的区域
  大多更差（B 组多个家族最好成绩 277–295；D 组最好成绩就是 BF 本身）。
- 多样性 ↑、分数 ↘：v4 没有带来改进，至少在单种子 32 次这个尺度上没有。
  不是实现 bug（记忆块正常工作、字数合规、方法记录完整），是设计取舍：
  当前记忆把“饱和”等同于“不要再试”，没有区分“饱和且最好”（值得精修）
  与“饱和且平庸”（应该避开）。
- 下一步（供明天定，不新开版本、不改代码的前提下可直接试的在前）：
  1. 改记忆文案的语义（仍属 v4 文本调整范畴，需另议是否算新版本）：
     最好家族标为“可精修”而非“避让”，避让只针对饱和且差的家族。
  2. 放宽记忆：只在家族尝试 ≥5 次且最好成绩差于当前最好时才避让。
  3. 更长的校准（100 次/组）：32 次可能不足以让搜索在避开甜带后
     再绕回来；但 100 次也可能只是更久地错过甜带，需配合 1 或 2。
  4. 给 basic 臂加记忆（A/C 目前 v4 提示词与 v1 相同，见上）：需要
     basic 提示词的记忆设计，是新版本工作。

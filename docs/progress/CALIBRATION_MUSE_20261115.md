## 怎么读这份结果（诚实版）

1. **search 集上四组都赢了 BF，但只赢了 0.1–0.2 箱。** 30 个实例的均值差
   0.1 箱 = 总共少用 3 个箱子，单一种子下很可能只是噪声，不能声称方法有效。
2. **validation 集上基本没赢。** 选中的候选：A/B 267.7，与 BF 完全持平；
   C/D 267.6，只好 0.1。这正是设 search/validation 分离的原因——search 集
   的小改进没有泛化。正式实验必须用多种子才能分辨信号和噪声。
3. **筛选的审计全数不符（3/3）。** C/D 共跳过 16 个候选，10% 审计只抽到 3 个，
   3 个的探针等价断言全部在完整评估里被推翻（计数或轨迹不符），指纹随即被禁用。
   样本很小，但方向明确：探针等价不可靠；正式分析里要如实报告这一点，审计率
   10% 在这个规模下只能抽到个位数样本。
4. **生成质量没问题。** 128/128 次响应都提取出了代码，0 无效候选，0 提供器错误。
   4 次格式违规全在 enhanced 组（Strategy 超 80 词之类），代码照常被评估。
5. **机制观察（只是观察，不是结论）：** search 集最优来自“甜带”家族——
   A/D 最优都是残留 [30,45] 奖励、[8,22] 惩罚的变体（265.1）；小残留惩罚类
   机制多次测下来都更差；D 组有 2 个候选（平方根/对数配对距离）与第 1 轮的
   线性配对距离排名完全相同，属于重复测试而非新多样性。

## 校准定下来的事

- 生成链路可靠：合法代码率 100%，0 错误，单次生成约 30–45 秒，四组并行
  每组 18–24 分钟跑完 32 次。正式规模跑得动。
- 费用 0 元（Muse 生成器）。时间是唯一成本。
- 审计样本太少：正式 run 如果保持 10% 审计率，50 次/组只能抽到约 5 个，
  对筛选的判断仍然很弱；报告里要写明这个局限，或者正式提高审计率（需改
  正式协议配置，改动要冻结前定下来）。
